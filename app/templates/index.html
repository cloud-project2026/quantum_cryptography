Setup Instructions — Enabling Post-Quantum Modes
1

Understand what's required

Post-Quantum TLS (Modes B and C) require OpenSSL 3.0 or later with the OQS Provider plugin loaded. Your current Python installation ships with OpenSSL 1.1.1, which was released before PQC standardisation.

2

Docker deployment (recommended path)

The included Dockerfile is based on Ubuntu 22.04 with OpenSSL 3.x. Build and run the container, then install oqs-provider inside it, or use the openquantumsafe/curl base image which already includes liboqs.

docker build -t pqc-lab .
docker run -p 5000:5000 pqc-lab
3

Ubuntu 22.04 / EC2 setup

On an Ubuntu VM, run the cloud setup script:

bash scripts/cloud_setup.sh

This installs OpenSSL 3.x, liboqs, oqs-provider, and the Python environment.

4

Verify PQC availability

After setup, restart the application and check this page again. Modes B and C should show Available.

Alternatively, from the command line:

openssl list -kem-algorithms | grep mlkem

Learn

Beginner-friendly explanations of the cryptographic concepts behind this project.

What is TLS?

TLS (Transport Layer Security) is the protocol that puts the "S" in HTTPS. Every time you visit a secure website, your browser and the server run a TLS handshake to:

  • Authenticate the server (using a digital certificate)
  • Agree on a shared secret key without ever sending it over the network
  • Use that key to encrypt all data exchanged

TLS 1.3 (2018) is the current standard. It is faster and more secure than older versions.

Classical Cryptography (X25519)

Today's internet uses elliptic-curve Diffie-Hellman (ECDH) for key exchange. X25519 is the most popular variant.

The security of ECDH relies on the Elliptic Curve Discrete Logarithm Problem — a mathematical problem that classical computers cannot solve in reasonable time, but that a sufficiently powerful quantum computer could solve using Shor's algorithm.

This is why we need post-quantum alternatives.

Post-Quantum Cryptography

Post-quantum cryptography (PQC) uses mathematical problems that are believed to be hard for both classical and quantum computers.

In 2024, NIST published FIPS 203 (ML-KEM), the first standardised post-quantum key-encapsulation mechanism. ML-KEM is based on the hardness of Module Learning With Errors (MLWE) — a lattice problem.

NIST FIPS 203

What is ML-KEM?

ML-KEM (Module Lattice Key Encapsulation Mechanism) is a KEM, not a full TLS cipher. In TLS, it replaces only the key-exchange step (deciding the shared secret). The bulk encryption algorithm (AES-GCM) stays the same.

ML-KEM comes in three security levels:

  • ML-KEM-512 — Level 1 (roughly equivalent to AES-128)
  • ML-KEM-768 — Level 3 (roughly AES-192) ← we use this
  • ML-KEM-1024 — Level 5 (roughly AES-256)

The trade-off: ML-KEM key material is larger than X25519 (1184 bytes vs 32 bytes), which may slightly increase handshake size.

Hybrid Key Exchange

A hybrid approach combines X25519 and ML-KEM-768 in the same handshake. The shared secret is derived from both algorithms combined.

This is the recommended migration strategy because:

  • If ML-KEM has an undiscovered flaw, X25519 still protects you.
  • If X25519 is broken by a quantum computer, ML-KEM still protects you.
  • Both algorithms must be broken simultaneously to compromise the session.

The IETF defines the hybrid group X25519MLKEM768 in an active draft.

Handshake Latency

Handshake latency is the time (in milliseconds) from when the client starts the SSL wrap until the TLS Finished message is received and keys are derived.

This platform measures:

  • TLS handshake time — the cryptographic operation itself
  • TCP connect time — recorded separately but NOT included in reported latency

We use Python's time.monotonic() which is a high-resolution clock that never goes backward — safe for performance measurement.

Why Migration Benchmarking Matters

Organisations cannot upgrade to post-quantum cryptography overnight because:

  • PQC algorithms are newer and less battle-tested.
  • Larger key sizes may impact performance on constrained devices.
  • Hybrid modes add overhead but reduce risk during the transition period.
  • Operators need real performance data to justify and plan upgrades.

This platform lets you measure those trade-offs in a controlled way and build an evidence base for migration decisions — which is exactly what NIST and industry guidance recommends.

Harvest Now, Decrypt Later

Even if quantum computers powerful enough to break encryption don't exist today, an adversary could record your encrypted traffic now and decrypt it later once they have a quantum computer.

This is called "Harvest Now, Decrypt Later" (HNDL) and is the reason migration is urgent for data that must remain confidential for 10+ years (government, medical, financial records).

Post-quantum key exchange addresses this threat because even future quantum computers cannot break ML-KEM with known algorithms.
